# 古いリポジトリからのデータ受け入れ基準

## 概要

このドキュメントは、古いリポジトリからこのリポジトリにデータを移行する際の受け入れ基準を定義します。

## 基本原則

1. **データの完全性**: 古いリポジトリのデータを完全に保持する
2. **プロキシアナンスの記録**: データの起源を記録する
3. **プラットフォームの分離**: 各プラットフォームのデータを分離する
4. **ライフサイクルの管理**: データの状態を明確に管理する
5. **品質の維持**: 移行後のデータ品質を維持する

## 受け入れ基準

### 1. データの分類基準

移行するデータは以下のカテゴリに分類する：

#### プラットフォーム別
- **YouTube**: 動画、チャンネル、アナリティクス
- **Instagram**: 投稿、ストーリーズ、リール、アナリティクス
- **Facebook**: 投稿、ページ、アナリティクス
- **X (Twitter)**: ツイート、アナリティクス
- **TikTok**: 動画、アナリティクス
- **CROSS_PLATFORM**: 複数プラットフォームにまたがるデータ

#### アーティファクトタイプ別
- **DATA**: 生データ、処理済みデータ
- **RESEARCH**: トレンド、キーワード、競合、オーディエンス調査
- **STRATEGY**: 戦略ドキュメント
- **CONTENT**: コンテンツ（アイデア、ブリーフ、ドラフト）
- **ASSET**: 画像、動画、音声などのアセット
- **CAMPAIGN**: キャンペーン関連データ
- **PUBLISHING**: 公開済みコンテンツの記録
- **EXPERIMENT**: 実験データ
- **REPORT**: レポート
- **CONFIGURATION**: 設定ファイル

### 2. プラットフォームの識別方法

各データアイテムに以下の情報を記録する：

```yaml
platform: [youtube|instagram|facebook|x|tiktok|cross_platform]
platform_specific_id: [プラットフォーム固有のID]
collection_date: [収集日]
observation_period: [観測期間]
source_tool: [収集ツール]
query_conditions: [クエリ条件（該当する場合）]
```

### 3. ライフサイクルの状態定義

#### データの状態
- **RAW**: 生データ（不変）
- **PROCESSED**: 処理済みデータ

#### コンテンツの状態
- **IDEA**: アイデア
- **BRIEF**: ブリーフ
- **DRAFT**: ドラフト
- **REVIEW**: レビュー中
- **APPROVED**: 承認済み
- **SCHEDULED**: スケジュール済み
- **PUBLISHED**: 公開済み

#### アセットの状態
- **SOURCE**: 元のアセット（不変）
- **WORKING**: 作業用アセット
- **APPROVED**: 承認済みアセット

### 4. 命名規則

#### ファイル命名
```
[日付]-[プラットフォーム]-[タイプ]-[説明].[拡張子]
```

例：
- `2026-09-18-x-cannabinoid-keyword-sample.csv`
- `2026-09-18-youtube-channel-metrics.csv`
- `2026-09-cannabinoid-trend-analysis.md`

#### ディレクトリ構造
```
data/<platform>/raw/          # 生データ
data/<platform>/processed/    # 処理済みデータ
research/trends/              # トレンド研究
research/keywords/            # キーワード研究
research/competitors/         # 競合研究
research/audiences/           # オーディエンス研究
content/ideas/                # アイデア
content/briefs/               # ブリーフ
content/drafts/               # ドラフト
content/calendar/             # カレンダー
assets/source/                # 元アセット
assets/working/               # 作業用アセット
assets/approved/              # 承認済みアセット
publishing/scheduled/         # スケジュール済み
publishing/published/         # 公開済み
campaigns/<campaign-id>/      # キャンペーン
experiments/                  # 実験
reports/weekly/               # 週次レポート
reports/monthly/              # 月次レポート
reports/quarterly/            # 四半期レポート
```

### 5. プロキシアナンスの記録

各データアイテムに以下のプロキシアナンス情報を記録する：

```yaml
provenance:
  source_platform: [元のプラットフォーム]
  collection_tool: [収集ツール]
  collection_date: [収集日]
  observation_period: [観測期間]
  query: [クエリ]
  sample_size: [サンプルサイズ]
  limitations: [制限事項]
  original_filename: [元のファイル名]
  migration_date: [移行日]
  migrated_by: [移行者]
```

### 6. 品質基準

#### 受け入れ条件
1. **完全性**: データが完全で、欠損がないこと
2. **一貫性**: データ形式が一貫していること
3. **正確性**: データが正確であること
4. **时效性**: データが適切な時間範囲内であること
5. **整合性**: データがリポジトリの構造と一致すること

#### 品質チェックリスト
- [ ] ファイル名が命名規則に従っているか
- [ ] プラットフォームが正しく識別されているか
- [ ] ライフサイクル状態が正しく分類されているか
- [ ] プロキシアナンス情報が記録されているか
- [ ] データ形式が正しいか
- [ ] 重複がないか
- [ ] エンコーディングが正しいか（UTF-8）

### 7. 拒否基準

以下のデータは受け入れない：

1. **不完全なデータ**: 欠損があるデータ
2. **不明なプラットフォーム**: プラットフォームが識別できないデータ
3. **不明なライフサイクル**: 状態が分類できないデータ
4. **品質の低いデータ**: エンコーディングが壊れている、フォーマットが不正
5. **重複データ**: 同じデータが複数ある場合（重複候として記録）
6. **機密情報**: APIキーやトークン、個人情報
7. **不正な形式**: 期待される形式と異なるデータ

## 移行手順

### フェーズ1：データの確認
1. 古いリポジトリのデータを確認
2. データの分類を実施
3. プラットフォームを識別
4. ライフサイクル状態を決定

### フェーズ2：データの準備
1. ファイル名を命名規則に従って変更
2. メタデータファイルを作成
3. プロキシアナンス情報を記録

### フェーズ3：データの配置
1. 適切なディレクトリに配置
2. READMEファイルを更新
3. メタデータを記録

### フェーズ4：検証
1. 品質チェックを実施
2. 整合性を確認
3. ドキュメントを更新

## 現在のリポジトリ構造との整合性

現在のリポジトリ構造は、README.mdで説明されている理想的な構造とは異なります。移行時に以下の点に注意する必要があります：

### 現在の構造
```
datasets/          # データセット
docs/              # ドキュメント
metadata/          # メタデータ
src/               # ソースコード
.github/           # GitHub関連
```

### 理想的な構造（README.md記載）
```
channels/          # チャンネル
research/          # 研究
data/              # データ
strategy/          # 戦略
content/           # コンテンツ
campaigns/         # キャンペーン
assets/            # アセット
publishing/        # 公開
experiments/       # 実験
reports/           # レポート
shared/            # 共有
scripts/           # スクリプト
archive/           # アーカイブ
```

### 移行計画
1. **datasets/** のデータを **data/** に移動
2. **docs/** のドキュメントを適切な場所に分散
3. **metadata/** のメタデータを **shared/schemas/** に移動
4. **src/** のスクリプトを **scripts/** に移動
5. 新しいディレクトリ構造を作成

## 注意事項

1. **生データの不変性**: 生データは絶対に変更しない
2. **歴史的記録の保持**: 古いデータも保持する
3. **プラットフォームの分離**: プラットフォームごとにデータを分離
4. **プロキシアナンスの記録**: データの起源を必ず記録
5. **品質の維持**: 移行後もデータ品質を維持
