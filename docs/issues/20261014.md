## 1. 目的

既存の投稿単位CSVを、研究上の分析能力を維持しながら、投稿者・元投稿の識別可能性を低減した公開用データセットに変換する。

次の要件を満たすこと。

1. 1投稿＝1行を維持する。 週次集計データへの置換は禁止。
2. 投稿ID、投稿者ID、投稿本文、URL等の直接識別情報を公開しない。
3. `createdAt` は削除せず、時間粒度を正規化して保持する。
4. 閲覧数、いいね数、リポスト数、返信数は共通の固定区間に変換する。
5. 研究の再現性、時系列分析、分布分析、分類分析、プラットフォーム比較を維持する。
6. 元データは非公開で保持し、GitHubには公開用データと変換仕様のみを配置する。

注意： 本実装はデータの非識別化処理であり、個人情報保護法上の「匿名加工情報」への適合を保証するものではない。コード・文書では `anonymized` を作業上の名称として使用できるが、法定の匿名加工情報と同義であると説明してはならない。

## 3. 列別の変換仕様

| 出力列               | 入力列                  | 変換規則                       |
| ----------------- | -------------------- | -------------------------- |
| `created_at_norm` | `createdAt`          | 日付を月単位に正規化。`YYYY-MM-01`    |
| `week`            | `week` / `createdAt` | ISO週の月曜日を `YYYY-MM-DD` で保持 |
| `compound`        | 収集メタデータ              | 検索対象成分。今回のデータは `CBX` を想定   |
| `platform`        | `platform`           | `x` に統一                    |
| `language`        | `language`, `lang`   | ISO 639-1の小文字に統一           |
| `views_bin`       | `views`              | 固定区間ビニング                   |
| `likes_bin`       | `likes`              | 固定区間ビニング                   |
| `reposts_bin`     | `reposts`            | 固定区間ビニング                   |
| `replies_bin`     | `replies`            | 固定区間ビニング                   |
| `has_text`        | `has_text`           | 真偽値として維持                   |
| `text_length_bin` | `text_length`        | 文字数を固定区間化                  |
| `topic_id`        | `topic_id`           | 分類IDを維持                    |
| `intent_id`       | `intent_id`          | 分類IDを維持                    |
| `format_id`       | `format_id`          | 分類IDを維持                    |

### 3-1. `createdAt` の正規化

採用方式：月初日への丸め込み（Monthly Date Normalization）

| 元の日時                   | `created_at_norm` |
| ---------------------- | ----------------- |
| `2026-08-03T09:21:35Z` | `2026-08-01`      |
| `2026-08-18T17:45:00Z` | `2026-08-01`      |
| `2026-09-02T02:10:00Z` | `2026-09-01`      |
| 欠損・不正値                 | 空欄                |

実装条件：

- 元日時はUTCとして解釈する。タイムゾーン付きの値はUTCに変換してから月を求める。
- タイムゾーンなしの日時については、既存データの仕様を確認するまで変換せず、検証エラーとして報告する。
- 日時の欠損を現在日時で補完しない。
- `created_at_norm` は月単位、`week` は週単位という異なる時間粒度を維持する。

補足： `week` が正確な週開始日を示す場合、`created_at_norm` の月単位化だけでは時間的な識別粒度は月単位にならない。公開レコード全体では週単位の時系列情報が残る。

### 3-2. `week` の正規化

- 週の開始日をISO 8601に従う月曜日とする。
- 形式は `YYYY-MM-DD`。
- `createdAt` が有効な場合は、その日時から週開始日を算出する。
- 既存の `week` と算出値が一致しない場合は差分を記録する。
- 既存の `week` が `unknown` でも、`createdAt` が有効なら補完可能とする。
- `createdAt` が無効で既存の `week` も不明なら空欄とする。推測による補完は禁止。

既存の `week` に3件の `unknown` があるという想定についても、実ファイルで確認すること。

## 4. エンゲージメント数の正規化

### 4-1. 固定区間ビニング

すべての反応数に同じ変換表を使用する。

| ビン値 | 元の件数        |
| --- | ----------- |
| 0   | 0           |
| 1   | 1～4         |
| 2   | 5～19        |
| 3   | 20～99       |
| 4   | 100～499     |
| 5   | 500～1,999   |
| 6   | 2,000～9,999 |
| 7   | 10,000以上    |

対象：

- `views`
- `likes`
- `reposts`
- `replies`

ビン境界はバージョン管理し、月別・成分別・プラットフォーム別に変更しないこと。

これにより、異なる期間のデータを同じ尺度で比較できる。

### 4-2. 欠損値の扱い

| 入力        | 出力                              |
| --------- | ------------------------------- |
| `0`       | `0`                             |
| 正の整数      | 対応するビン値                         |
| 空欄 / NULL | 空欄                              |
| 負数        | 検証エラー                           |
| 数値でない文字列  | 検証エラー                           |
| 小数        | 原データ仕様を確認し、整数として扱える根拠がなければ検証エラー |

欠損とゼロを混同しないこと。

### 4-3. 正規化の禁止事項

- Min-MaxやZ-scoreだけを適用して匿名化済みとみなさない。
- 元の正確な数値を別列に残さない。
- ビン値から推定した中央値を実測値として扱わない。
- 月ごとに分位数を再計算しない。
- ノイズを無断で追加しない。

## 5. 文字数の正規化

`text_length` は次の固定区間に変換する。

| `text_length_bin` | 文字数     |
| ----------------- | ------- |
| 0                 | 0       |
| 1                 | 1～20    |
| 2                 | 21～50   |
| 3                 | 51～100  |
| 4                 | 101～200 |
| 5                 | 201～280 |
| 6                 | 281以上   |

文字数の定義は、既存の `text_length` の計算仕様に合わせること。Unicodeコードポイント数、UTF-16コード単位数、表示上の文字数を混在させない。

## 6. 識別情報の除去

以下は公開CSVへの出力を禁止する。

| 情報              | 取扱い         |
| --------------- | ----------- |
| 投稿ID・ハッシュ化投稿ID  | 削除          |
| 投稿者ID・仮名ID      | 削除          |
| ユーザー名・表示名       | 削除          |
| 投稿URL・プロフィールURL | 削除          |
| 投稿本文            | 削除          |
| 画像・動画URL        | 削除          |
| 正確な投稿日時         | 削除          |
| 正確なエンゲージメント数    | ビニング後の値のみ出力 |
| Cookie・認証情報     | 出力禁止        |
| 内部の元データ対応表      | 非公開         |

許可リスト方式で14列だけを書き出すこと。 入力の全列をコピーしてから不要列を削除する方式は採用しない。

## 7. 分類情報と研究上の再現性

`topic_id`、`intent_id`、`format_id` は保持する。

実装条件：

- 分類IDの意味を定義したコードブックを公開する。
- 分類ルール、分類器のバージョン、適用日を記録する。
- 欠損と「分類不能」を区別する。
- 分類IDの値を月別に変更しない。
- 既存の分類結果を匿名化処理の中で再分類しない。

`compound` は収集対象を示すメタデータから設定する。ファイル名からの自動推測のみで確定してはならない。

## 8. 再識別可能性の検査

直接識別子を削除しても、投稿時期、反応量、分類ラベルの組み合わせが一意になる可能性がある。

したがって、公開前に以下を検査する。

| 検査       | 内容                        |
| -------- | ------------------------- |
| 単一レコード識別 | 属性の組み合わせが一意となる行数          |
| 少数グループ   | 同一属性の組み合わせが2件以下のグループ数     |
| 時間的識別    | `week` と分類・反応ビンの組み合わせ     |
| 特異値      | 最大ビンや稀少分類の出現状況            |
| 直接識別子    | ID、URL、本文、ユーザー名が出力されていないか |

検査結果は、次の3段階で報告する。

- `PASS`：定義済みの公開基準を満たす
- `REVIEW`：一意性・少数セルなどの確認が必要
- `FAIL`：禁止列、未変換値、処理不整合などが存在

重要： k-匿名性などの基準値は現段階では未決定。実装者が独断で基準値を設定したり、レコードを削除・統合したりしてはならない。
