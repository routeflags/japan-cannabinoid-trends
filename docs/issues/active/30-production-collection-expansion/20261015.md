## 1. 目的

Japan Cannabinoid Trends研究プロジェクトにおけるX投稿データの収集を、第三者製スクレイピングActorから\*\*X公式API（X API v2）\*\*へ移行する。

本実装では、次の3点を重視する。

1. **正規性**：X公式APIとDeveloper Agreement / Developer Policyに従って取得する。
2. **研究再現性**：データ取得・加工・分析の手順と実行証跡を保存する。
3. **データ管理**：X 元投稿データはリポジトリに保存せず、取得手順・機密除去済み証跡・派生集計だけを管理する。

研究方法論はHutton & Hendersonの提案する **Method / Code / Data** の区別を参考とする。

**取得手順の再実行可能性と、元データの完全な再現性は区別すること。**

## 3. X公式APIへの移行

### 3.1 認証

X Developer Consoleで発行されたBearer Tokenを使用する。

環境変数：

`X_BEARER_TOKEN`

要件：

- 認証情報をソースコードに記載しない。
- `.env` 等の秘密情報ファイルをGit管理対象から除外する。
- ログ、VCR、例外メッセージにBearer Tokenを出力しない。
- 認証情報の存在とAPIへの接続を検証する。

### 3.2 APIエンドポイント

`GET https://api.x.com/2/tweets/search/all`

既に実行した接続試験では、Full-Archive Searchから投稿データを取得できている。

基本的なリクエスト例：

```
curl -G 'https://api.x.com/2/tweets/search/all' \
  -H "Authorization: Bearer $X_BEARER_TOKEN" \
  --data-urlencode 'query=CBX lang:ja' \
  --data-urlencode 'start_time=2025-01-01T00:00:00Z' \
  --data-urlencode 'end_time=2025-02-01T00:00:00Z' \
  --data-urlencode 'tweet.fields=created_at,public_metrics,lang' \
  --data-urlencode 'max_results=100'
```

### 3.3 ページネーション

- `meta.next_token` によるページネーションに対応する。
- 全ページの取得条件と取得件数を記録する。
- ページの欠落、重複取得を検出する。
- APIエラー時は途中結果を成功扱いしない。
- 再試行によるリクエスト回数と取得件数を考慮する。

### 3.4 API利用と課金条件

X API は従量課金の経路であり、本リポジトリの実行は課金の発生しない経路に限る。
単価・予算額・請求額は記録しない（`AGENTS.md` Scope Exclusion: Cost）。

**owner 決定（2026-10-15）:** 基盤完成まではリポジトリ内の実行経路を
mock / dry-run に限定し、X の live request は禁止する。
live 実行に進む場合は、request-only evidence（`ISS-20261015-PRV-033`）が通った後、別途明示承認を取る。

実装要件：

- 取得予定件数を事前に見積もる。
- 実行単位の取得件数とリクエスト回数を記録する。
- 件数の上限を設け、上限到達時には新規リクエストを停止する。

HTTP 402（支払い要求）、429、401、403 をそれぞれ適切に処理する。

## 4. データ管理方針

### 4.1 公開禁止

X APIから取得した以下のデータは、公開リポジトリへ出力しない。

- 投稿ID
- 投稿者ID
- 投稿本文
- 投稿URL
- 投稿単位のエンゲージメント指標
- 投稿単位の匿名化・正規化CSV
- APIレスポンス本文
- 元投稿に対応付けられる内部データ

**匿名化した場合でも、投稿単位の研究CSVは公開しない。**

### 4.2 リポジトリ保存禁止と境界

X 元投稿データは、公開 / 非公開、tracked / untracked、`data/private/` の別を問わず、リポジトリ配下に保存しない。

DDD 的には次を分ける。

| 概念 | 扱い |
|---|---|
| X 元投稿データ（投稿 ID、投稿者 ID、本文、URL、投稿単位 engagement、API レスポンス本文、元投稿に対応付く投稿単位レコード） | リポジトリ保存禁止 |
| 取得リクエスト証跡（本文・ID・token 原値を除いた endpoint/query/期間/status/件数/token digest 等） | Request-only evidence として保存可 |
| 派生集計（投稿単位を復元できない粗い集計） | publication review / gate 後に公開候補化可 |
| 分析・変換コード、方法論、コードブック | 追跡可 |

したがって、本リポジトリ内の「保持期間・更新頻度・削除条件」は X 元投稿データには定義しない。禁止なので保持しない。外部で一時的に取得処理が必要な場合も、リポジトリ artifact として採用せず、機密除去済みの request-only evidence と派生集計だけを記録対象にする。

### 4.3 公開可能な成果物

以下を公開対象とする。

- API取得手順
- 検索条件・サンプリング方法
- データ変換・分析コード
- 分類体系とコードブック
- 研究方法論
- APIリクエストの証跡（機密情報を除去したもの）
- 規約上公開が認められる集計結果
- 研究上の限界と再現性に関する説明

公開対象に含めた情報であっても、Xの規約上の制約がある場合はそれを優先する。

## 5. Request-only VCRの実装

### 5.1 目的

API取得時の通信条件と実行結果を記録し、研究の取得プロトコルを検証可能にする。

**HTTPレスポンス本文は記録しない。**

VCR.py等を使用する場合、標準のレスポンス記録機能をそのまま使用しないこと。

### 5.2 記録項目

| 項目               | 保存 |
| ---------------- | -- |
| APIエンドポイント       | ○  |
| HTTPメソッド         | ○  |
| 検索クエリ            | ○  |
| 開始・終了日時          | ○  |
| リクエスト実行日時        | ○  |
| ページ番号            | ○  |
| HTTPステータス        | ○  |
| 取得件数             | ○  |
| レスポンス処理時間        | ○  |
| APIエラー種別         | ○  |
| 実行ID             | ○  |
| 取得コードのGitコミット    | ○  |
| Bearer Token     | ×  |
| 投稿ID・投稿者ID       | ×  |
| 投稿本文             | ×  |
| レスポンス本文          | ×  |
| `next_token` の原値 | ×  |

ログの公開前には、検索クエリを含め、個人情報・機密情報・再配布制限対象の情報が混入していないか検証すること。

### 5.3 証跡の完全性

- 取得処理と同時にログを生成する。
- JSON Lines形式等の機械可読な形式で記録する。
- 実行IDで複数リクエストを関連付ける。
- 実行完了時にログファイルのSHA-256を計算する。
- ハッシュとGitコミットを記録する。
- ログの欠落を検出する。

ハッシュは改変検出の補助であり、取得データの正確性や実行時刻の真正性を単独で保証するものではない。

## 6. 研究データ処理

取得データに対して、既存研究の処理を適用する。

- 収集対象成分の分類
- 週次・月次時系列処理

- エンゲージメント分析
- `topic_id` / `intent_id` / `format_id` の分類

分析に必要な投稿単位のデータは、許可された保持範囲内で非公開処理する。

**既存の研究指標、分類ルール、集計方法は変更しないこと。**

変更が必要な場合は、変更理由と研究結果への影響を提示し、承認を得る。

### 7.3 Data

元の投稿データは公開しない。

研究成果では、次の限界を明示する。

> 本研究では、X公式APIを用いたデータ取得手順、処理コードおよび実行証跡を公開する。一方、投稿単位の元データはプラットフォームの利用条件に従って非公開とする。したがって、取得手順の再実行可能性を提供するが、同一データセットおよび分析結果の完全な再現性は保証しない。

### 指示書の内部で確認した点（実装前に解くべき緊張）

- §3.3 は「全ページの取得条件と件数を記録」を要求し、§5.2 は `next_token` の**原値を保存しない**。
  連続性・欠落・重複の検出はトークン原値以外の手段（ページ番号・トークンのダイジェスト・
  件数の累計）で満たす設計が要る。
- §6 は「既存の研究指標・分類・集計方法を変更しない」としつつ、収集手段を Apify から公式 API へ
  替える。**収集手段の変更は来歴上の変更**（collector_id / adapter_id / 観測コーパスの差）なので、
  既存コーパスと新コーパスを混ぜずに記録する必要がある（受け皿は G5 の run provenance）。
- §2 の対象期間 2021〜2026 は、既存 X データ（2026-08〜09 収集）とは**別の取得**になる。同一研究の
  継続として扱うなら研究方法論への追記が要る（§7.3 の限界文と併せて）。
