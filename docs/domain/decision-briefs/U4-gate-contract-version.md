# U4 判断材料: ゲート契約の版未宣言（G1）

**状態:** owner決定済み（2026-10-16: 案C「未宣言維持 + トリガー条件を正式化」を採用）。G1 は意図的に open の既知ギャップとして残す。本書 §3 のトリガー条件は正式方針であり、案ではない。
**親文書:** `docs/domain/context-map.md` §4 U4・§5、方針の正本は `docs/specs/contracts.md` §9・§10。
**実測日:** 2026-10-16（台帳現物の引用。推測で補わない）。

## 1. 用語の確認（混同しないこと）

- **版（バージョン）:** 契約の意味的同一性を識別する表示。「バージョンを持つ」とは次の3点が揃うこと（context-map §5）。1つでも欠ければ未宣言である。
  1. 版の値が宣言場所に存在する。
  2. 台帳 `contract-ledger` の `version` 列に記録される（`None` は未宣言の記録）。
  3. 検査がバージョンの一致を検証する。
- **リリース:** 版の配布単位・配布行為（git tag / Zenodo。例 v1.13.x）。契約の版管理とは別の関心事であり、「ゲートに版を付ける」は「ゲートをリリースする」ではない。
- よって「ゲート契約に版を付与する」とは、**定数＋台帳列＋一致検査の1組を新設すること**であり、定数だけ置くことではない。

## 2. 現状実測（Observed）

- ゲート契約は **7 件**（`docs/audits/contract-ledger.json` の `summary.by_kind.gate_contract = 7`。`contracts.md` §8 の「6件」は 2026-10-15 時点の日付つき実測であり、現行台帳は `gate-release-manifest` を含む7件）。
- 7 件すべて `version: None`。台帳の gap 8 件のうち7件がゲートの `version_undeclared`（残り1件は reader 契約 G2）。`tests/validation/test_contract_ledger.py::test_gaps_are_derived_from_the_declarations` がこの導出を機械的に固定している。
- 各ゲートの宣言場所には版定数がなく、`declared_at`（モジュールパス）のみがある（`src/validation/contract_ledger.py` の `GATE_CONTRACTS`）。バージョン一致を検証する検査は存在しない。CLI 自体が判定する。
- 方針（`contracts.md` §10）: **版が必要になった時点で付与し、推測で付けない。** 未宣言のまま記録するのが現状の正しい状態である。

## 3. 版を付ける条件（付与トリガー。owner承認済みの正式方針）

次のいずれかが成立した時点を「必要になった時点」とする。現状はいずれも不成立である。成立の認定は owner が行い、成立した場合は owner がゲート契約バージョン付与を再判断する。G1 はその判断まで意図的に open のまま残す。

| # | トリガー | 成立条件 | 現状 |
|---|---|---|---|
| T1 | 意味変更トリガー | gate の合否意味、必須条件、failure / warning の扱いが変わる場合 | 不成立。各ゲート単一実装、意味変更の予定なし |
| T2 | 並存トリガー | 同一 gate 名について複数の判定基準を同時に保持・実行・参照する必要が出た場合 | 不成立。並存なし |
| T3 | 引用トリガー | 外部公開・DOI・論文・第三者監査で gate 判定基準を固定識別子として引用する必要が出た場合 | 不成立。引用需要なし（gate 版を指す欄は存在しない） |

用語制約（§1 の定義に照らす）: **版（バージョン）とリリースを混同しない。** リリース（版の配布単位・配布行為。git tag / Zenodo）するからといって gate version が必要になるわけではない。T3 が問うのは「gate 判定基準を固定識別子として引用する必要」が出たかどうかであり、DOI・論文・監査への言及そのものではない。version 導入はトリガー成立時の再判断事項である。

T1–T3 は旧案の番号を引き継いで正式化したものである（旧 T1 判定条件の追加・削除等→ T1、旧 T2 並存→ T2、旧 T3 run・監査記録の引用→ T3 に明確化）。

## 4. 付けない場合の安全策（現状維持で担保されていること）

- 未宣言は `version: None`＋gap として可視化され続け、手書き一覧で消えることはない（台帳導出＋上記テストが固定）。
- ゲートの意味変更は既存の振る舞いテスト（各ゲートの `test` 列: `test_gates.py`、`test_pipeline.py`、`test_coverage.py`、`test_comparability.py`、`test_research_catalog.py`、`test_publication_gate.py`、`test_release_manifest.py`）と監査 freshness で検出する。版がなくても無検査ではない。
- 「必要になった時点」の認定は人間の責務として `docs/domain/contracts/contract.md` の Escalation に記録済み。黙って版を付けることも、黙って閉じることもしない。

## 5. 付ける場合に必要な変更（1組の新設。抜けがあると版にならない）

1. **版定数:** 宣言場所に版の値を置く。対象7箇所: `src/validation/gates.py`（gate-plan / gate-run の2件）、`coverage.py`、`comparability.py`、`src/research/comparability.py`、`publication_eligibility.py`、`release_manifest.py`。一括単一版かゲートごと個別版かは別途決定（U4-Q3）。
2. **台帳列:** `GATE_CONTRACTS` の `version` に配線し、`contract-ledger.json` を再生成する。
3. **一致検査:** `check_schema_version`（CV-20）に相当するゲート版一致検査を新設し、実行場所を決める（gate 出力への版刻印か、`audit-new-runs` 等での検証か）。
4. **記録側の引用:** 判定を受けた run・artifact 側に準拠版を明記する欄（現行の `adapter_contract_version` 等に相当）。スキーマ変更を伴う可能性があり、最も影響が大きい。
5. **併存・廃止方針:** context-map §5 の3要件（台帳は各版を区別／検査は対象版を指定・検証／記録は準拠版を明記、廃止は別途宣言）を満たす運用にする。
6. **文書＋テスト:** `contracts.md` §9手順・§10、context-map §5、台帳再生成、`test_contract_ledger.py` への gate 版 parity 検査追加、freshness（`test_audit_report_freshness.py`）の green。

## 6. 選択肢と影響

### 選択肢 A: 未宣言のままにする（G1 を開けたまま維持）

- **状態:** **採用（案Cの一部として。単独案としては C に吸収）。**
- **内容:** §10 方針どおり、T1–T3 が成立するまで版を付けない。G1 は既知ギャップとして残る。
- **メリット:** 推測版付けをしない方針と整合。移行リスクゼロ。版の形だけ作って中身（検査・引用）が伴わない「見せかけの版」を避けられる。
- **リスク・影響:** G1 が開き続ける。ゲート意味変更の検出は振る舞いテスト頼みであり、版不一致としての検出はできない。
- **追加テスト候補:** なし（現行テストがそのまま担保）。T1–T3 のいずれかが成立したかを将来の変更レビューで問うチェックリスト運用で足りる。

### 選択肢 B: 今すぐ版を付与する（G1 を閉じる）

- **状態:** **不採用（今回は見送り。T1–T3 のいずれかが成立した時点での再検討とする）。**
- **内容:** 7 件に版（例: 一括 `1.0.0`）を付け、上記 §5 の1–6を全部実施する。
- **メリット:** G1 が閉じる。将来の意味変更が版不一致として検出可能になる。
- **リスク・影響:** 並存需要のない版付けは投機的であり、§10 方針との整合説明が要る。変更範囲が大きい（7定数＋台帳＋新検査＋記録欄＋文書＋テスト）。記録欄（§5-4）はスキーマ変更波及の可能性があり、最も重い。検査・引用が伴わなければ番号だけの版になる。
- **追加テスト候補:** gate 版 parity 検査（台帳版＝宣言定数）、版一致検査の新規テスト、freshness 再 green、全 suite。

### 選択肢 C: トリガー条件だけ先に定義する（中間案）

- **状態:** **採用（owner決定 2026-10-16）。版は付けず、§3 の T1–T3 を正式方針として記録する。G1 は開けたまま。**
- **メリット:** 「必要になった時点」が誰でも判定可能になる。コード変更ゼロに近い。A の安全策に明確な出口条件が付く。
- **リスク・影響:** G1 自体は残る。トリガー承認が得られなければ A と同じ。
- **追加テスト候補:** なし。トリガー成立時の手順チェックリスト（§5 の1–6）を文書として用意する。

## 7. 決定記録（owner決定 2026-10-16）

**選択肢 C（未宣言維持 + トリガー T1–T3 の正式化）を採用する。** G1 は閉じない。意図的に open の既知ギャップとして残す。理由: 並存も引用需要もない現状で版の1組を新設するのは §10 の「推測で付けない」に反し、費用対効果が悪い。一方で「いつ付けるか」を正式方針として合意しておけば、G1 を開けたままにすることの出口条件が明確になる。B は T1–T3 のいずれかが成立した時点での再検討で足りる。
