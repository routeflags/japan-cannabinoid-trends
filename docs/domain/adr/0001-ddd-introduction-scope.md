# ADR-0001: DDD導入の範囲と進め方

**状態:** 受理（2026-10-16）  
**対象:** `docs/domain/` の新設文書群。既存コード・正本仕様の変更は含まない。

## 背景

`docs/specs/contracts.md`（版1.2.0 §2・§3・§5）は既にユビキタス言語・コンテキストマップ・DDD対応表を持ち、
DDD導入はゼロからの新設ではなく「既存の境界言語をDDDの形で運用可能にする」作業である。
スキル `ddd-architect`（`.github/skills/ddd-architect/SKILL.md`）を本リポジトリに配置して実行した。

## 決定

1. 範囲は Balanced（glossary＋context-map＋エージェント契約＋境界テスト1件＋パイロット1件）。
   ソース再構成は行わない（フォルダ合わせの再構成禁止）。
2. キーワードは owner 選定の4件（生産・研究・加工・契約）に、バージョン・リリースを加えた6語を glossary とする。
3. U1（加工の独立性）・U2（ゲート契約の所有＝契約）は owner 決定で解決済み。U2 の正本同期は残件。
4. 「版」→「リリース」改名は巻き戻した。版≡バージョン（別概念）、リリース＝配布単位（git tag / Zenodo）。
5. 境界テストT1（P5方向：gate 判定モジュールは生産の生成コードに依存しない）を `tests/domain/` に置く。
   逆方向（生産が pre/post gate を呼ぶ構造）は U5 で解決済み：生産は契約遵守のために検証ゲートを呼び、結果を執行しなければならない。
6. パイロットは次回の加工出力再構築（`platform-trends` 等）とし、`processing.md` の越境手順どおりに実施して手順の不足を記録する。
7. サブドメイン分類は owner 決定により、研究管理基盤を core とする。研究管理基盤は「研究対象データの形成、評価、公開までのライフサイクルを、来歴・契約・検証・制約とともに管理し、再現可能な研究リリースを成立させる中核能力」と定義する。

## 根拠

- 2026-10-16 の保守（`8195e71`）は結果的に processing 契約の手順（再構築→スナップショット再生成→期待値更新）と同形だった。
  手順化の有効性は実証済みであり、パイロットはその追試と位置づける。
- T1 は AST による静的検査（stdlib のみ）。現状で通過すること（2026-10-16 実測：`validation`→`collection` の module-level import は0件）を Choose ではなく Measure で確認した。

## 帰結

- `docs/domain/` は既存テストの走査対象外（audits / issues のみ）のため、追加・巻き戻しはテストに影響しない（2026-10-16 全 suite green で確認）。
- ロールバック条件：本ADR配下のコミットを revert する。ランタイム・データへの影響は原理的にない。
- 残件：U2正本同期、U3（隣接記録のみ）、U4（G1）。
